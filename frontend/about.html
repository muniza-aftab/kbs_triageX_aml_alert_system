Demonstration system. Built for a portfolio, not for compliance use. It has no regulatory approval and has never seen a real case.

How it works

This is a rule-based system, not a trained model. Every decision it makes can be traced back through named rules to the facts of the case. There is no step where a number comes out of something nobody can inspect.

It reasons in stages, not in one jump

The easiest way to build something like this is one big table: certain inputs go in, a verdict comes out. That is also the least useful way, because nobody can tell why it said what it said, and it cannot express partial conclusions.

So this system works up through stages instead. Each stage may only read from the stages below it, a rule is rejected at build time if it tries to skip ahead.

Stage What it produces
1. Measurements Plain arithmetic about the case. How many payments, how large, how quickly the money left, how old the account is.
2. Observations Named things that are true of the activity. "Payments cluster just under a review threshold." No opinion about what it means yet.
3. Patterns Recognised laundering methods the observations are consistent with, each with a strength. This is where interpretation starts.
4. Assessment Is the evidence complete? Is any of this outside what the system can judge? Does a legal obligation apply?
5. Risk The overall risk posture, combining pattern strength with context.
6. Decision One of the five actions, chosen by a fixed order of precedence.

A worked chain, from an actual example:

Facts. Fourteen cash deposits of £2,400 over six days. Account opened three weeks ago. No evidence on file of where the money came from.

Observations. Deposit frequency is extreme. Each deposit sits just under the £3,000 review threshold. The total is far larger than any single deposit. The account is too new to have a normal pattern.

Pattern. This is strongly consistent with splitting deposits to stay under a threshold.

Assessment. Evidence is incomplete: the source of the money is not documented. Everything else about the case is assessable.

Decision. Request evidence. Specifically: ask for source-of-funds documentation, which is the least intrusive thing that would settle it.

It works out what to ask for

When the system asks for evidence, it has not picked from a fixed list. It searches every combination of evidence the bank could obtain, weighs each by how much effort it takes and how intrusive it is for the customer, and returns the cheapest combination that would actually change the decision.

So a sanctions screen, quick, internal, no contact with the customer, is preferred over a full interview, unless only the interview would settle the matter.

It also reports honestly when nothing would help. If a case involves cryptoasset transfers, no amount of paperwork gives this system a model of how those flows work, so it says the case cannot be resolved rather than inventing a request.

It can explain why it did not do something

The useful question is rarely "why did you say that". It is "why didn't you close it". That cannot be answered by showing the reasoning that was used, because the answer is about something absent.

Every assessment on this site therefore lists each other decision it could have reached and what specifically stopped it, for example: "Evidence on file is Incomplete, and would need to be Complete."

It checks itself

A separate tool inspects the rules themselves, looking for the sort of defect no individual test case would reveal: two rules that contradict each other, a rule that can never fire, a conclusion nothing is able to reach.

It has found real problems. The most instructive was a rule that recorded a UK public figure as a foreign one. Every case still produced a defensible decision, so no test caught it, the error was in what a fact meant, not in any outcome.

What it is built from

The rules are derived from published material rather than invented: the Proceeds of Crime Act 2002, the Money Laundering Regulations 2017, guidance from the Joint Money Laundering Steering Group and the Financial Conduct Authority, and typology work from the Financial Action Task Force and the Wolfsberg Group.

Each rule records where it came from, and is tagged by how directly:

From legislation For example, a confirmed sanctions match must always be escalated.
From published guidance For example, what "splitting deposits" looks like in practice.
Reconstructed The shape comes from guidance; the numbers were set for this project. This is the largest group, and saying so plainly matters.

That last category is unavoidable. Published guidance describes what suspicious behaviour looks like but deliberately leaves the actual thresholds to each firm's own risk appetite, so there was nothing to copy. Every number in this system was chosen to be plausible.

What it cannot do

It has never seen a real case

Every example is invented, and every "correct answer" was decided by the same person who wrote the rules. The performance figures on this site measure whether the system is internally consistent. They are not evidence that it would work on real alerts.

  • Four kinds of laundering are deliberately excluded, trade-based laundering, cryptoasset ramps, correspondent banking and trust structures. This is not a gap to be filled later: a system that claims to cover everything cannot meaningfully say "this is outside what can be assessed".
  • It cannot see intent. It concludes that behaviour matches a pattern, never that someone meant to launder money. Nothing in transaction data shows intent, and claiming otherwise would be dishonest about what the system can see.
  • It considers one customer and one alert at a time. Real monitoring looks across accounts, across customers and over months. This does not.
  • Its thresholds are untested for sensitivity. The numbers are plausible, but nobody has measured how much the conclusions would move if they were set differently. That is the largest known gap.

One result that went against the design

The system was built expecting that it should also decline when a decision was simply close, near the boundary between two conclusions. That was implemented and measured, and it made things worse at every setting tested.

The reason is instructive. The system already gets about 98% of the cases it answers right, so declining the marginal ones throws away correct answers about as often as wrong ones.

What does pay is declining for a specific, nameable reason, something outside its competence, a check that has not been run. In short: knowing what you do not know is worth a great deal. Knowing only that you are unsure is worth nothing.
